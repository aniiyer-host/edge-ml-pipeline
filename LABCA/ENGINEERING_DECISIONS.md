# Edge AI Gesture Recognition Project - Engineering Decision Table

This document captures key engineering decisions made during the project, including alternatives considered, observations that led to the decision, final choice, and reasoning.

## Sensor Configuration Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Gyroscope Range | ±250°/s, ±500°/s, ±1000°/s, ±2000°/s | Lower ranges (±250°/s, ±500°/s) saturated during wrist rotation gestures, causing clipping and loss of dynamic information | ±1000°/s | Avoids sensor saturation during fast wrist rotations while maintaining sufficient resolution for gesture classification (±1000°/s gave readings up to ~822°/s without clipping) |
| Accelerometer Range | ±2g, ±4g, ±8g, ±16g | ±2g provided sufficient resolution for human hand gestures without excessive noise; higher ranges unnecessary for target motions | ±2g | Optimal balance of resolution and range for human-scale accelerations in gesture recognition |
| Sampling Frequency | 25Hz, 50Hz, 100Hz, 200Hz | 50Hz chosen as Nyquist-appropriate for human gesture frequencies (<25Hz); lower frequencies risked aliasing, higher frequencies increased power/data burden without benefit | 50Hz | Matches typical human motion bandwidth while balancing power consumption and data throughput |
| Window Size | 25 samples (0.5s), 50 samples (1.0s), 75 samples (1.5s), 100 samples (2.0s) | 50 samples captured complete gesture temporal dynamics; smaller windows missed full motion profiles, larger windows increased latency unnecessarily | 50 samples (1 second) | Optimal trade-off between capturing full gesture dynamics and maintaining low latency for real-time interaction |
| Sensor Axes | 3-axis (accel only), 6-axis (accel+gyro), 9-axis (add magnetometer) | Gyroscope data provided critical rotational information that accelerometer alone could not distinguish (e.g., wrist rotation vs idle); magnetometer unnecessary for indoor use and prone to interference | 6-axis (ax,ay,az,gx,gy,gz) | Combines translational and rotational motion sensing for comprehensive gesture characterization |

## Hardware Implementation Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Microcontroller | ESP8266, ESP32, Arduino Uno, STM32 | ESP32 chosen for better processing power, native WiFi, and sufficient RAM for TensorFlow Lite Micro; ESP8266 considered but limited resources; Arduino Uno insufficient for ML | ESP32-WROOM | Provides adequate computational headroom for feature extraction and inference while maintaining low cost and WiFi connectivity |
| IMU Sensor | MPU6050, MPU9250, BMI160, ADXL345+ITG3200 | MPU6050 selected for proven reliability, adequate performance, and extensive community support; MPU9250 considered but magnetometer interference indoors made it less beneficial | MPU6050/GY-521 | Optimal balance of performance, cost, availability, and ease of integration for 6-axis motion sensing |
| Communication Protocol | I2C, SPI, UART | I2C chosen for simplicity (2 wires), adequate bandwidth for 50Hz sampling, and widespread library support; SPI considered but unnecessary complexity for data rates | I2C (SDA=GPIO21, SCL=GPIO22) | Minimal pin usage, sufficient bandwidth (300 values/sec @ 50Hz), and robust ecosystem |
| Power Source | USB 5V, LiPo battery, coin cell | USB power selected for development and testing convenience; battery options considered for final wearable form factor but deferred to future work | USB 5V (development) | Stable power supply for iterative development and testing; battery integration left as future enhancement |
| Data Transmission | Serial UART, UDP WiFi, Bluetooth, NFC | UDP WiFi selected for reliable wireless transmission to PC with reasonable latency; Bluetooth considered but added complexity; Serial UART limited to tethered use | UDP over WiFi | Enables wireless operation with PC-based inference while maintaining transmission reliability |

## Machine Learning Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Model Type | Decision Tree, Random Forest, SVM, GNB, 1D CNN, 2D CNN, RNN/LSTM | 1D CNN selected for temporal feature extraction capability; tree-based models insufficient for capturing temporal patterns; 2D CNN inappropriate for 1D time series data; RNN/LSTM overly complex for limited data | 1D CNN | Best trade-off between temporal modeling capability and parameter efficiency for resource-constrained deployment |
| Input Representation | Raw values, FFT features, statistical features (mean/std), engineered features | Raw temporal sequences preserved for CNN to learn automatic features; statistical features lost temporal information; engineered features required manual domain expertise | Raw 6-channel time series (50×6) | Allows automatic feature learning from temporal patterns without manual feature engineering |
| Architecture Depth | 1 Conv block, 2 Conv blocks, 3 Conv blocks, 4 Conv blocks | 3 Conv blocks provided optimal feature hierarchy; 2 blocks insufficient for complex pattern recognition; 4 blocks risked overfitting on limited dataset | 3 Conv1D blocks (32→64→64 filters) | Progressive feature extraction with adequate model capacity while controlling parameter count |
| Regularization | None, Dropout only, BatchNorm only, Dropout+BatchNorm, L1/L2 regularization | Combination of Dropout and BatchNormalization provided best generalization; neither alone sufficient; L1/L2 less effective for this architecture | BatchNorm + Dropout (0.3 rate) | Synergistic regularization: BatchNorm stabilizes training, Dropout prevents overfitting |
| Pooling Strategy | MaxPooling only, AveragePooling only, GlobalAveragePooling only, No pooling (flatten) | GlobalAveragePooling1D selected to dramatically reduce parameters while preserving spatial information; MaxPooling alone required large Dense layers; flattening caused parameter explosion | GlobalAveragePooling1D after Conv blocks | Reduces parameters from ~100K to ~15K by eliminating need for large Dense layers after convolutional feature extraction |
| Classification Head | Single Dense layer, Two Dense layers, Three Dense layers | Two Dense layers (64→n_classes) provided sufficient capacity; single layer insufficient for complex mapping; three layers risked overfitting | Dense(64) → Dropout → Dense(n_classes) | Balanced classification capacity with intermediate representation learning |
| Activation Functions | ReLU only, Tanh only, Sigmoid only, LeakyReLU, PReLU | ReLU selected for standard performance and computational efficiency; alternatives showed no significant benefit for this architecture | ReLU throughout (except final softmax) | Industry standard activation with good gradient properties and computational efficiency |
| Optimizer | SGD, Adam, RMSprop, AdaGrad | Adam selected for adaptive learning rates and robust convergence; SGD required careful tuning; RMSprop less effective on sparse gradients | Adam (lr=1e-3) | Reliable convergence with minimal hyperparameter tuning required |
| Loss Function | Categorical Crossentropy, Sparse Categorical Crossentropy, KLDivergence | Sparse Categorical Crossentropy selected for integer label efficiency; equivalent to categorical but memory-efficient for large class counts | Sparse Categorical Crossentropy | Memory and computational efficiency with integer-encoded labels |
| Evaluation Metric | Accuracy, F1-score, Precision/Recall, AUC | Accuracy selected as primary metric for balanced dataset; per-class metrics considered but overall accuracy sufficient for initial validation | Accuracy (with confusion matrix analysis) | For balanced gesture classes, accuracy provides intuitive performance measure; confusion matrix used for detailed error analysis |

## Data Processing Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Data Collection Method | Continuous recording, windowed recording, event-triggered | Windowed recording selected to enforce fixed-size training examples; continuous recording required complex segmentation; event-triggered missed preparatory motions | Fixed 50-sample windows triggered by serial command | Ensures uniform training example size while allowing gesture timing variability within window |
| Labeling Strategy | Per-sample labeling, per-window labeling, gesture-boundary labeling | Per-window labeling selected for simplicity and alignment with classification approach; per-sample labeling required temporal smoothing; boundary labeling complex to implement | Single label per 50-sample window | Matches model input structure and simplifies training pipeline |
| Normalization | None, Min-Max scaling, StandardScaler, RobustScaler, per-channel scaling | StandardScaler selected for zero-mean unit-variance properties beneficial for neural networks; Min-Max sensitive to outliers; RobustScaler unnecessary for clean IMU data | StandardScaler (fit on training data only) | Centers features and scales variance for stable neural network training; prevents features with large ranges from dominating gradients |
| Train/Val/Test Split | 60/20/20, 70/15/15, 80/10/10, stratified vs random | Stratified 70/15/15 split selected to maintain class distribution while ensuring adequate validation/testing; non-stratified risked class imbalance in splits | Stratified 70% train, 15% val, 15% test | Preserves class representation across splits for reliable performance estimation; validation size sufficient for early stopping |
| Data Augmentation | None, time warping, jittering, scaling, window slicing | No augmentation applied initially to establish baseline; considered but deferred until baseline performance established | No augmentation (baseline first) | Establish true baseline performance before introducing augmentation complexity |
| Outlier Handling | Remove windows, clip values, interpolate, keep raw | Decision to reject entire corrupted windows rather than modify samples; clipping loses information; interpolation creates artificial data | Reject complete window if any sample appears corrupted | Preserves data integrity principle: never modify raw training data; maintains audit trail of collection process |
| Temporal Alignment | Fixed gesture start, random within window, variable padding | Variable gesture timing within window selected to prevent model from learning positional memorization; fixed start risked overfitting to position; variable padding complex to implement | Natural timing variation within 50-sample window | Prevents overfitting to specific temporal positions; encourages learning of gesture-invariant temporal patterns |

## Deployment Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Inference Location | On-device (ESP32), PC-based, cloud-based | PC-based inference selected for initial validation due to easier debugging and iteration; on-device considered for final deployment; cloud rejected for latency and privacy concerns | PC-based inference (UDP→TFLite→MQTT) | Enables rapid iteration and debugging while validating end-to-end pipeline; on-device migration planned for future work |
| Model Format | Keras (.h5), TensorFlow SavedModel, TFLite float32, TFLite INT8, C array | TFLite INT8 selected for 4x size reduction with minimal accuracy impact; float32 considered but too large for deployment; C array required for Arduino embedding | INT8 TFLite + C header export | Achieves deployment size targets (<30KB) while preserving accuracy; C header enables direct ESP32 embedding |
| Quantization Strategy | Float32, dynamic range INT8, full integer INT8, float16 | Full integer INT8 selected for maximum compression and MCU compatibility; dynamic range less effective; float16 insufficient compression | Full integer INT8 quantization with representative dataset | Maximizes size reduction while maintaining compatibility with ARM Cortex-M MCUs used in ESP32 |
| Model Size Target | <50KB, <30KB, <20KB, <10KB | <30KB target selected as achievable for ESP32 while maintaining accuracy; <20KB considered too restrictive for initial version | Target: <30KB weights | Balances deployment feasibility with model capacity for gesture recognition task |
| Latency Budget | <100ms, <50ms, <20ms, <10ms | <100ms end-to-end latency selected as acceptable for interactive applications; <50mm considered ideal but challenging; <10ms unrealistic for feature extraction | Target: <100ms end-to-end latency | Matches human perception thresholds for responsive interaction while being achievable on target hardware |
| Communication Reliability | Best-effort UDP, acknowledged UDP, TCP, MQTT direct | Best-effort UDP selected for simplicity and low overhead; acknowledged UDP considered but added complexity; TCP excessive for streaming; MQTT direct duplicated infrastructure | Best-effort UDP with sequence numbers | Provides lightweight transmission with application-level loss detection via sequence numbers |

## Gesture Set Decisions

| Decision | Alternatives | Observation | Final Choice | Reason |
|----------|--------------|-------------|--------------|--------|
| Initial Gesture Set | 5 classes (wave L/R, flick U/D, idle), 6 classes (+fist_hold), 7 classes (+wrist_rotate), 8+ classes | Pilot data showed fist_hold overlapped significantly with idle; wrist_rotate showed distinct patterns; 6 classes provided optimal separability | 6 classes: idle, wave_left, wave_right, flick_up, flick_down, wrist_rotate | Maximizes class separability while minimizing ambiguous classifications; fist_hold removed due to insufficient motion distinction from idle |
| Class Naming | Technical descriptors, user-action descriptors, symbolic names | User-action descriptors selected for intuitive understanding and communication; technical descriptors less accessible; symbolic names required mapping | Descriptive action names (wave_left, flick_up, etc.) | Enhances usability and communication clarity; directly maps to user-performed actions |
| Idle Class Definition | No motion threshold, specific rest pose, any non-gesture motion | Specific rest pose selected for reproducible baseline; no-motion threshold too ambiguous; any non-gesture motion introduced variability | Defined resting hand position | Provides consistent baseline for model to distinguish from active gestures; reduces false positives from natural hand tremor |
| Similarity Thresholds | Binary classification, probability threshold, distance-based metrics | Probability threshold selected for simplicity and compatibility with softmax output; distance metrics required embedding space; binary insufficient for confidence | Softmax probability with configurable threshold | Enables confidence-based rejection of ambiguous predictions; threshold tunable for precision/recall trade-off |
